## 已确认问题

### F39 / P2：异常重分配后，打印拣货单混入已取消分配

- 位置：`web/src/utils/documentPrint.ts:45–67`，`outboundPrint`把`data.allocations`全部直接映射为“按原分配行核对拣货”，没有分配状态列或历史说明。
- 真实流程：40/20件入库→创建5件出库并审核→登记1件货损且确认未发实物退回→重新分配。接口保留一条CANCELLED历史和一条ALLOCATED当前分配，这是正确审计记录。
- 页面从出库详情点击“打印预览”，却列出两条同库位/批次的5件分配，均未标识取消；原单仍只需要5件。纸面核对可能误用旧尝试。此处没有实际执行两次扣库，不能据此认定库存已经错账。
- 修复方向：作业清单只列当前可执行分配；若保留已发/已取消历史，应独立标明状态与用途，不能无状态混入当前拣货数量。补异常恢复后的真实打印预览回归。

### F40 / P2：冻结、解冻、短缺流水筛选后无法导出

- 位置：`internal/modules/inventory/dto/export.go:15`的`TransExportQuery.TransType`只允许旧8种类型；页面`TRANS_TYPE_OPTIONS`已包含FREEZE、UNFREEZE、SHORTAGE。
- 真实浏览器进入库存流水，选择这三种类型后点击“导出Excel”，每种均实际发出GET `/inventory/trans/export?trans_type=...`并返回HTTP400、参数错误。FREEZE/UNFREEZE准备了真实流水；SHORTAGE即使当前筛选无行也应允许导出空表，不能拒绝合法枚举。
- 未筛类型的导出仍可使用；不是整个导出系统不可用。修复应对齐类型白名单，并在HTTP层遍历全部正式流水类型校验，不能只测Service绕过绑定。

### F41 / P2：库存Excel的货品ID被导出成0

- 位置：`internal/modules/inventory/repository/export.go:21`的`ExportStockRow.SKUID`没有`gorm:"column:sku_id"`；查询实际投影`i.sku_id`。与之前F36同类映射遗漏，但发生在独立的导出投影，不是已修复的预警列表回归。
- 真实MySQL→Service→Excelize回读：货品1101的库存导出第7列“货品ID”为文本`0`，名称/编码仍正确。已有导出测试检查行数、库存ID、条码和租户，没有断言货品ID。
- 不修改数据库库存，但导出后无法可靠按ID关联货品。修复为显式列映射，补真实XLSX单元格身份断言及大ID字符串保存。

### F42 / P2：同会话正常续期被误判为登录身份变化

- 位置：`web/src/stores/auth.ts:160–164`每次`setDemoSession`都递增`sessionVersion`；Demo心跳对同一个session_id也调用它。新组件使用该版本判断身份切换。
- 真实浏览器：演示账号打开货品条码标签预览，正常交互触发心跳；响应仍是同一个session_id，版本却递增，标签预览随后自行关闭。核对版本变化并等待Element Plus关闭动画完成后确认；仅在网络响应刚返回时立即判断可见会产生假通过。
- 两项真实composable受控异步回归分别验证`useClosureCommands`和`useWaveCommands`：命令进行中同会话续期后busy变false；随后合法成功回执被忽略，返回null，pending仍存在，且没有明确错误提示。没有发现因此重复写库。
- 同一版本还被导出取消、AI停止和业务确认使用，存在同类影响的静态调用链，但这些入口未逐一动态复现，不追加独立缺陷计数。
- 修复方向：续期只更新TTL；仅会话ID实际变化或真正重新登录/退出时推进身份代次。保留同token重新登录以及旧401/70003不清新会话的保护，并补同会话续期与真实换身份的对照测试。

### F43 / P2：正常冻结库存被工程演示误报为不守恒

- 位置：`internal/modules/demo/service/experiment_allocation.go:286–311`的统计及`concurrentInventoryInvariantOK`仍使用三数量公式，遗漏frozen_quantity；库存充足、短缺、拣货实验共用该函数。
- 真实流程：演示账号将SKU000001正常冻结1件，再运行2单×1件并发分配实验。实验完成但返回`invariant_ok=false`，提示库存不变量异常；重新读取真实库存，每行均满足`stock=available+allocated+frozen`。
- 这是假告警，不是本轮查出实际错账。修复需一并补冻结量统计、非负核对、接口/页面展示和说明；不要以忽略不变量校验来消除错误提示。性能页同样未展示冻结量，静态记录为同组口径检查项。

### F44 / P2：移库成功回执仅判断ID非空，非法ID会清掉原请求

- 位置：`web/src/composables/useStockMove.ts:50–53`及`:74–76`；send与check以`!id`判断合法性，字符串`"0"`仍通过。
- 故障注入通过真实浏览器提交移库，先`route.fetch()`转发到真实服务并确认提交，仅把成功回执中的移库ID改为字符串`"0"`，其余参数保持真实原值。页面仍显示完成，并把原pending清掉；预期应保留原参数/key供核对。
- 此项证据是受控回执损坏，不是正常后端会生成0，也没有证明本次重复移动。它与F33的回执保护原则相同，但移库入口未完整接入严格ID校验；按恢复可靠性P2登记，不升级为已发生错账。
- 修复应复用`isReceiptID`核对移库记录及必要库存ID，同时保留请求对象/数量/原因校验；send和只读核对都补合法、非法、大ID测试，异常回执不得解除恢复保护。
