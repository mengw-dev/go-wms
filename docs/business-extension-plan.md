# 业务能力扩展计划（不新增中间件）

[文档导航](README.md) · [现有迭代与工程待办](iterations.md) · [需求与边界](requirements.md)

制定日期：2026-10-21。状态：**计划已制定，各阶段均待开发**。本文安排新增业务能力，不把现有工程债或未验收能力标记为完成。本轮只写计划，不修改业务代码。

## 1. 目标与执行原则

沿用 Go + Vue + MySQL + Redis，不新增需要独立部署的服务。允许按需增加普通代码依赖、数据库表和进程内后台任务；新增表必须通过正式迁移，并同步开发建表契约。

- 优先打通打印、扫码、导出和异常处理，按阶段形成可独立使用、验证和交付的成果。
- 保留白天靛紫与夜间深蓝绿，继续适配电脑和手机；打印输出使用独立的白底样式。
- 库存写入、FIFO、事务锁、任务租约及幂等继续使用现有业务入口。新增界面、扫码或后台任务不能绕开它们。
- 新增能力覆盖权限、租户隔离、失败反馈和可追溯记录；后台作业与收货/上架/拣货作业任务区分管理。
- 不为展示策略模式、责任链而重构已稳定的核心事务。出现真实的多种规则后，再提取小接口或函数。
- 一次实施一个阶段。启动阶段前核对代码与相关未关闭问题；如果相关缺陷会影响验收，优先修复。每阶段通过验收后再进入下一阶段。
- 不承诺固定日期，按实际业务规则、打印机/设备条件和验证结果安排。提交、推送与发布遵循当次用户要求。

## 3. F01：单据、标签打印与扫码

### F01.1 单据打印

- 入库单、出库拣货单、盘点单提供打印入口和预览；字段来自有权限访问的真实单据。
- 首期采用 A4 单据样板，覆盖单号、仓库、状态、明细、数量及必要说明。
- 打印时去掉导航、筛选、演示浮条和操作按钮，处理分页、重复表头和长字段换行。
- 打印是只读行为，不改变单据状态、库存、任务或幂等记录；打印按钮不能把打印对话框关闭视为“已打印成功”。

### F01.2 货品与库位条码标签

- 在货品和库位页支持单张/选中记录批量标签预览与打印。
- 内部编码优先评估 Code 128；已有商品条码保留原值、原编码规则，不把任意内部编码当作标准商品码。
- 标签显示可读名称和编码；编码不满足所选码制时明确提示。标签尺寸先做一种样板，实际投用前按打印机、纸张与扫描结果确定。
- 条码载荷明确区分货品与库位，保留前导零；租户和权限由服务端身份核对，不信任码内传入的租户信息。

### F01.3 扫码接入现有作业

- 先支持键盘型扫码枪/手动输入与回车提交查询；手机摄像头扫码作为后续子项，不作为首期前置条件。
- 扫码识别后展示匹配对象和当前任务，继续走现有收货、上架、拣货的校验与确认流程。
- 错码、错库位、错批次、无权限或查无记录有明确反馈；重复扫码不直接增加已提交数量。
- 写入继续复用现有幂等 key 与结果未知恢复流程，不把扫描事件自动等同于库存变更。

**验收：** 打印预览与单据数据一致，长明细跨页可读；标签可在目标设备识别；原有扫码核对和数量操作不回归，重复确认不会重复扣增库存；跨租户/无权限不能读取对应对象。没有真实打印机/扫码枪时，只记录浏览器与模拟输入通过，保留实机验收项。

**首期边界：** 不做静默打印、打印机驱动管理、电子面单供应商对接或可视化模板设计器；确需这些能力时另定设备和客户端方案。

## 4. F02：Excel 导出与后台作业

### F02.1 有上限的基础导出

- 先提供库存明细、库存流水、盘点差异导出，再按需求增加入出库明细。
- 导出遵循服务端校验后的仓库、SKU、批次、日期等条件，明确是全部匹配记录还是当前页；不得默认把当前页伪装为全部结果。
- 明确字段、数量上限、时区与统计时间；编码、条码和长 ID 以文本保存，日期、数量采用约定格式。
- 不把用户文本解释为公式；空结果和超限给出清晰反馈，不生成缺页却标为成功的文件。
- 已有导入流程优先复用现有失败明细接口；按实际缺口增加可下载的错误行、原因与修正说明，不重复建设导入解析器。

### F02.2 按规模增加异步导出

- 达到明确的数据量或耗时门槛后，再引入导出后台作业，避免首期就建设通用任务平台。
- MySQL 保存作业、查询条件、执行权 token、进度、重试信息和文件元数据；进程内有限并发 worker 执行，借鉴已有导入 worker 的执行权校验。
- 提供待处理、处理中、成功、失败、已过期等状态；支持受控重试，进程重启后可恢复，旧 worker 不能覆盖新执行结果。
- 文件保存至持久化目录，下载重新核对租户、权限与有效期；明确单实例/同一持久卷的边界。
- 声明导出的一致性口径：首期可采用读取期间的数据并标注生成时间；需要严格时点快照时单独设计，不无条件长时间持有业务事务。

**验收：** 筛选、总量和样例数据可核对；长 ID/前导零无损；越权下载被拒绝；超限和失败不返回假成功。实施异步子项时补充抢占、重启、重试、文件缺失和过期清理验证。

## 5. F03：业务异常处理

- 首期规则：创建超过配置阈值仍未完成的作业任务、导入/导出失败；低可用库存按明确阈值单独配置，不混用不同商品单位。
- 出库分配失败等异常先确认现有失败证据是否可查询；缺少记录时先补事件记录，不能仅凭当前单据状态推测失败原因。
- 每条异常显示触发原因、原始对象、所属仓库、时间、当前处理状态和原业务入口。
- 首期先做汇总与跳转，确需分派/确认时再增加持久记录；同一持续异常去重，恢复后再次发生应能形成新的发生记录。
- 处理后重新核对原业务结果。人工确认/忽略不等于库存问题已解决，也不自动取消单据或释放库存。
- 仪表盘只展示必要的异常摘要，详情留在处理页；页面明确展示规则阈值，避免将“创建时长”宣传为没有约定的 SLA 超时。

**验收：** 异常能追溯、同一持续问题不刷屏、恢复后状态可核对、权限与租户隔离有效；处理入口继续调用既有业务流程。

## 6. F04：波次拣货与规则

- 首期人工选择同租户、同仓库、满足状态条件的订单，建立波次与单据/现有拣货任务的关联。
- 展示波次进度与逐单结果。已有审核产生的分配记录继续有效，加入波次不重复分配库存或创建重复任务。
- 后续按真实需求增加同 SKU、库区、截止时间等分组规则，再提取可替换的分组策略。多个规则的执行顺序和匹配后是否终止需明确。
- 合并展示的拣货数量仍需落实到原单据/任务，不能丢失批次、库存归属或原幂等语义。
- 退出/撤销波次默认只影响关联，不隐式取消业务订单、释放分配或撤销已完成拣货；有关状态变更单独定义和验收。
- FIFO/FEFO 属于库存分配规则，与波次分组分开。FEFO 要先增加并验证有效期数据，不把入库时间当成到期时间。
- 路径规划后置：先有可通行通道和库位坐标，再区分两点间寻路与多个拣货点的访问顺序优化；未验证全局最优时不称“最短总路线”。

**验收：** 不可重复加入不兼容波次；并发创建、撤销、原订单取消、部分完成等情形有确定规则；原库存/分配/任务数量守恒且不跨租户或仓库。

## 7. F05：设备状态与告警试点（可选）

- 先选一种可通过 HTTPS 接入的设备或模拟器，不直接建设通用物联网平台；仅支持其他协议的真实设备需另行确定接入方案。
- 设备登记仓库、类型与独立凭证；上报接口校验身份、租户和允许的指标。
- 保存服务端最近接收时间、在线/超时未上报状态，以及设备支持的电量、温湿度或故障指标；收到心跳不等于设备所有功能健康。
- Redis 保存最新状态，MySQL 保存低频历史和告警事件；明确采样、历史保留期限、聚合与清理，避免无限写入。
- 规则支持阈值持续一段时间再触发、持续异常去重和恢复记录；处理重复/乱序上报，不让旧数据覆盖最新状态。
- 前端先采用受控轮询，确有实时性要求再考虑 SSE；不引入 MQTT Broker、InfluxDB 或 MQ。
- 模拟器与真实设备明确区分，模拟页面不可宣称已经完成现场硬件联调。

**验收：** 上报、超时、超限、恢复形成可演示闭环；越权/重复/乱序上报被正确处理，最新状态与历史口径一致。真实硬件接入和高频大规模容量验证单列，不由模拟试点替代。
