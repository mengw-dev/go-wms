# 基础波次与播种拣货

本功能已纳入 main 合集，入口为“出库管理 → 波次与拣货”。原普通逐单拣货继续保留。当前合并验证见[开发记录](development.md)，推送与目标环境上线分别核对。

## 操作流程

1. 正常创建、提交、审核出库单，让 FIFO 完成库存分配。
2. 新建波次，选择一个仓库。可手动勾选订单，也可按创建时间从早到晚预选最多 50 单。预览后可调整勾选，确认提交的是具体订单 ID；创建时在事务内重新校验，预览不锁定订单。
3. 领取波次。作业员租约为 10 分钟，可以续领；过期后其他作业员可接手，并应现场交接实物。
4. 汇总拣货：按来源库存行（货品、库位、批次）合并需求，扫描或手动核对货品编码/条码、库位、批次和本次数量。支持部分登记，全部行完成后进入分货。
5. 播种分货：按出库单分配的软件槽位 `S01...S50`，核对货品、批次、槽位和本次数量。支持部分登记，不串批次，不跨订单挪用已分数量。
6. 某订单分货完成即可显式确认该单发货，无需等待其他订单分货；所有订单发货后波次完成。发货前应核对实物并完成实际交接。

FIFO 决定从哪些库存批次分配；波次和播种决定如何组织现场拣货，两者同时存在。这里的“一键按规则组波”是人工触发的选单预览，不是定时自动建波。

## 库存与任务口径

汇总拣货、播种分货分别记录在波次行和分货项，原库存继续在来源库位保持占用。实物拣出后视为本波次逻辑暂存，不新建暂存库位库存；界面和打印单中的库位表示**来源库位**。

确认发货时，同一事务内扣减 `stock_quantity` 和 `allocated_quantity`、记录 SHIP 流水、完成原分配行和拣货任务、推进原出库单、记录波次成员发货时间并写幂等结果。`stock_quantity = available_quantity + allocated_quantity` 保持成立。

原任务的 `done_qty` 和出库单的 `picked_qty` 在波次确认发货时完成，不代表波次现场已拣/已分进度；现场进度应看工作台。加入波次后，原普通拣货、PDA 领取和订单取消入口拒绝处理，出库单详情提供工作台入口。

仅未登记任何拣货的波次可以撤销，撤销会解除成员关系、恢复普通拣货，**不取消原订单、不释放原库存分配**。已开始拣货的退回、短拣、数量纠错与异常撤波不在本基础版本内，应完成现场核对后继续流程，不能通过清数据库处理。

## 状态、权限及规模

`CREATED → PICKING → SORTING → READY → COMPLETED`；第一笔一次拣完全部行可直接到 SORTING。仅 CREATED 可转 CANCELLED。成员订单可在 SORTING 或 READY 逐单发货。

| 动作 | 权限 |
| --- | --- |
| 列表、候选和详情 | `wms:outbound:view` |
| 建波、撤销 | `wms:outbound:approve` |
| 领取、汇总拣货、分货、发货 | `wms:outbound:pick` |

每波 1–50 单、最多 1000 条原拣货任务；同一精确租户、同一仓库，只接受已全部分配且尚未拣货、未持有效普通领取租约、未进入其他波次的订单。不提供波内增删单、跨仓波次、复杂策略、最短路径、定时调度、硬件播种墙或新中间件。

## API 与幂等

所有路径以 `/api/v1` 开头。所有写操作必须携带 1–64 字符 `Idempotency-Key`，成功返回 `{ "wave_id": "字符串ID" }`，客户端再刷新详情。

| 方法 | 路径 | 含义 |
| --- | --- | --- |
| GET | `/outbound/waves` | warehouse_id、keyword、page、page_size（最多100） |
| GET | `/outbound/waves/candidates` | warehouse_id 必填、keyword、limit（默认20，最多50） |
| GET | `/outbound/waves/:id` | 波次、订单槽位、汇总行、分货项 |
| POST | `/outbound/waves` | order_ids（字符串数组）、remark |
| POST | `/outbound/waves/:id/claim` | 领取/续领 |
| POST | `/outbound/waves/:id/cancel` | 撤销尚未开始的波次 |
| POST | `/outbound/waves/:id/lines/:part/collect` | qty、sku_code（可条码）、location_code、batch_no |
| POST | `/outbound/waves/:id/items/:part/sort` | qty、sku_code（可条码）、batch_no、slot_code |
| POST | `/outbound/waves/:id/orders/:part/ship` | 确认成员订单发货 |

`outbound.wave` scope 使用动作、作业员和归一化参数生成 v2 指纹。幂等成功记录与业务原子提交；回滚后新读核对已提交结果。业务事务首先锁定任务或波次头，不能先做会固定 RR 快照的普通幂等查询，否则等待锁后可能读到旧进度。不同 key 的重复发货仍由成员已发货状态拦住。

前端按账号/演示会话持久化一笔未确认波次命令。刷新、网络失败后必须用原参数和原 key 恢复；超过 7 天或记录损坏禁止自动重发。放弃本机记录不撤销后端业务。浏览器存储不提供跨标签页互斥，服务器以行锁、数量边界和幂等记录最终裁决。

## 迁移与发布边界

`000015_wave_picking` 增加 `wms_task.wave_id` 和 `wms_wave / wms_wave_order / wms_wave_line / wms_wave_item`。正式启动要求两项波次数量 CHECK 存在且启用，开发 AutoMigrate 与版本迁移的列类型保持一致。

正式版本顺序为库存预警 `000013`、仓内移库 `000014`、波次 `000015`。原波次开发分支的未发布 `000014_wave_picking` 已顺延，不能同时执行两个同号迁移。若曾手工试运行旧波次候选库，须核对实际表结构并按迁移规程单独升级，不能直接把候选库当作本版的14。原工作区未提交的外部单候选不在合集内；不要混用未提交迁移构建正式包。

发布前排空旧应用实例：旧版本不了解 wave_id，混合运行可能仍通过旧入口拣货。已有波次数据后禁止直接回滚到旧应用。down 迁移仅允许完全没有波次历史时执行；有历史会先拒绝，迁移工具可能标记 dirty，需核对失败原因和数据库状态后按迁移规程处理，不能强制删除历史或直接清 dirty。

仓库上架的排他门锁没有在本功能修改，仍为既有 B16 并发边界，见[规模验证](scale-validation.md)。
