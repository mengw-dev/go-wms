# 出库规模与仓库锁验证（D25）

2026-10-25后续修正：仓库/SKU引用已改为共享锁，库位及库存行仍排他保护，波次按仓库→SKU顺序锁引用。下文仓库门锁及23.244/5.239ms数据保留为2026-10-21历史实验，不能作为当前协议的性能结论。新协议并发、删除保护及业务回归见[锁与逻辑修复](locking-logic-audit-20261025.md)；D25的规模上限与目标环境验收边界继续有效。

验证日期：2026-10-21。基线为本地提交 `e187287`；修复版本为该基线加本轮 D25 改动，排除其他未提交业务改动。仅连接独立本机测试实例，各用例创建并删除自己的临时库，未访问生产库。

## 生效边界

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `limits.max_shipment_details` | 200 | 单张出库单明细条数；手工、内部与外部新建入口共用，审核历史单也校验 |
| `limits.max_allocation_rows` | 1000 | 单次审核所有明细累计占用的库存行数，同时限制生成的分配记录及拣货任务数 |

两项同时约束普通租户和平台租户，不是访客总单量配额；遗漏或非正数恢复默认值，不代表无限制。环境变量见 [配置参考](configuration.md)。提高数值前，应在目标硬件、数据分布和并发下复验。

新建超明细上限返回 HTTP 400 / 50020，提示拆单。审核最多读取明细上限加一行，发现历史大单即拒绝；累计分配超限返回 HTTP 400 / 50021，提示拆单或整理分散库存。数量上限与 FIFO 顺序不变。已经修改的库存、明细和流水与订单/分配/任务一起回滚，不截断成部分成功。

降低配置后，既有单仍可查询、取消；外部同号同内容回放可以核对原有的超限明细，不重新建单。超长回放请求必须先匹配历史单的实际明细条数，不能仅借用一个普通业务号绕过新建解析预算。历史单超新上限不能继续审核，需要拆单或经目标环境复验后调整配置。

## 受控审核实验

Windows amd64、Go 1.26.9、MySQL 8.0.46，Ryzen 7 7840H（8 核 / 16 逻辑处理器），InnoDB buffer pool 128 MiB，RR 隔离。单进程串行服务调用，每个场景一个私有数据库，每种规模 5 次。每个 SKU 的库存批次数量均为 1，每个库存行对应一个库位；每次先创建/提交订单，仅计时 `Approve`，确认任务、分配、ALLOCATE 流水数量，再走业务取消释放库存。

| 明细数 | 每明细库存行数 | 总分配行数 | 基线中位 / 最大 ms | 修复后中位 / 最大 ms |
| --- | --- | --- | --- | --- |
| 1 | 1 | 1 | 5.224 / 8.667 | 4.373 / 6.176 |
| 50 | 1 | 50 | 121.762 / 130.780 | 103.720 / 108.185 |
| 200 | 1 | 200 | 470.787 / 497.150 | 418.242 / 474.983 |
| 1 | 250 | 250 | 231.586 / 244.197 | 207.912 / 222.450 |
| 1 | 1000 | 1000 | 782.935 / 913.144 | 769.129 / 829.328 |
| 200 | 5 | 1000 | 1076.605 / 1174.826 | 1141.959 / 1276.746 |

结论是成本随明细和批次增加，适合先设置有界的默认处理规模；这次没有改变分配算法，不将样本间差异解释为性能提升。5 次样本不报告 P95/P99。这不是 HTTP、持久运行、并发大单、真实上架整链或生产容量 SLA，也没有证明所有合法库存分布都在同一时间内完成。

额外回归覆盖单明细超预算、多明细累计超预算、最后一条明细无剩余预算、恰好到预算、连续拒绝无残留、提高预算后成功重试及取消恢复；另覆盖新建明细超限、历史审核拒绝、外部历史回放和配置默认/环境变量。

## 仓库锁与查询计划

`TestIncreaseWarehouseGate` 先持有指定仓库行的排他锁，直接从 MySQL `performance_schema.data_lock_waits/data_locks` 观察同仓 Increase 的实际等待；另一仓库能完成，释放持锁事务后原操作继续并提交两条库存及两条流水。观察等待耗时包含人为持锁和轮询，不当作普通请求延迟。

8 个并发 Increase、各用独立 SKU/库位、库存四元组已存在的单次实验：同仓整批 23.244 ms，分仓 5.239 ms。该实验隔离仓库门锁；初始新四元组插入实验还观察到缺失行范围锁的 1213，事务重试后成功，不能将所有争用都归因于仓库锁或据一次样本承诺提速。现有 D24 真实死锁/超时回归继续适用。

保留仓库→库位→SKU 的删除/禁用保护协议；真实上架入口本身也锁仓库，单独移除 Increase 的仓库锁无法消除整条上架链的同仓串行，还会破坏保护协议。本轮选择维持一致性、限制大事务和保留观测；更细锁粒度需要在明确吞吐目标下整体设计并复验。

`TestInventoryScalePlan` 使用嵌入式正式迁移建库，写入 1 万条、10 租户/100 SKU 的混合库存，目标条件匹配 100 条，执行 ANALYZE TABLE。对实际 FIFO 条件的首批和键集续页分别记录 EXPLAIN FORMAT=TREE / EXPLAIN ANALYZE，并验证真实 repository 每批取 20 条、续页无重叠。本次优化器选择 `idx_inv_tenant_sku`，扫描 100 条再排序，首批输出 20 条、续页过滤剩余 80 条再输出 20 条；本次读查询约 0.14–0.33 ms，不是锁定读取或审核总时间。仍有排序，但未观察全表扫描，不据此强制索引或新增迁移。

小规模/全表同 SKU 数据也可能合理地选择全表扫描加排序；不同数据分布与统计信息可选其他索引，测试不固定计划字符串。持续索引审查归 D27。

## 重现入口

仅使用可创建临时库的专用测试 MySQL 账号；仓库锁观测用例还需要读取上述 performance_schema 表。

```powershell
$env:WMS_TEST_REQUIRED = '1'
$env:WMS_TEST_DSN = '<独立测试 MySQL DSN>'
$env:WMS_SCALE_PROFILE = '1'
go test ./internal/app -run 'Test(OutboundScaleProfile|InventoryScalePlan)' -v -count=1 -timeout=180s
go test ./internal/modules/inventory/service -run 'TestIncreaseWarehouse' -v -count=1
Remove-Item Env:WMS_SCALE_PROFILE
go test ./internal/app ./internal/pkg/config -run 'Test(OutboundAllocationBudgetRollback|OutboundDetailScaleAndExternalReplay|ShipmentScaleConfiguration)' -v -count=1
```

不开启 `WMS_SCALE_PROFILE` 时，全量回归每种审核规模仅跑一次，不设置受机器速度影响的耗时断言。本地原始日志位于忽略目录 `tmpgen/scale-boundary-20261021`；关键条件与结果已记录在本文，不依赖该目录阅读结论。
