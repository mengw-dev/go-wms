# 数据库引用完整性说明

这份文档说明当前 WMS 的引用完整性策略和设计取舍。

## 当前策略

引用完整性主要由**应用层**维护，而非数据库外键约束。

### 原因

1. **多租户共享表**：所有业务表按 tenant_id 隔离，外键约束无法表达"跨租户不允许引用"这一业务规则。应用层在事务内锁定并核对引用对象属于同一租户。

2. **库存一致性**：库存三数量等式（`stock = available + allocated`）由 Service 层事务 + 行锁 + CHECK 约束共同保证。外键 cascade 会绕过 Service 层的事务逻辑，可能破坏库存流水与库存行的一致性。

3. **删除安全**：仓库、库位、SKU 的删除需先检查库存、任务、单据、分配和历史引用。应用层在同一事务内行锁检查，拒绝有引用的数据删除。外键 cascade 或 restrict 无法表达"零库存但仍有库存历史行也拒绝删除"这类复合规则。

4. **迁移灵活性**：golang-migrate 版本化迁移在空库上从 000001 一路执行。不加外键降低了迁移间的依赖复杂度，避免加列/改索引时外键约束阻塞。

### 已有的数据库层约束

| 约束类型 | 位置 | 说明 |
| --- | --- | --- |
| 唯一索引 | 各业务表 | 防止重复编码、重名角色等 |
| CHECK 约束 | `wms_inventory` | `chk_inv_non_negative`、`chk_inv_allocated_non_negative`、`chk_inv_quantity_balance` |
| 软删 + 唯一索引 | 带.deleted_at 的表 | 防止软删后重建同名行冲突 |
| tenant_id 索引 | 所有业务表 | 支撑租户过滤 |

### 应用层引用检查

| 操作 | 检查方式 |
| --- | --- |
| 删除仓库 | 同事务内检查库位、SKU、库存、任务、单据引用 |
| 删除库位 | 同事务内检查库存行引用 |
| 删除 SKU | 同事务内检查库存、单据明细、任务引用 |
| 删除角色 | 同事务内检查用户角色关联 |
| 库存创建 | 同事务内锁定仓库、库位、SKU，防止删除与创建形成孤儿引用 |

## 生产化可选方案

如果将来需要加强引用完整性：

1. **核心强关系加 FK**：如 `wms_inventory.warehouse_id → wms_warehouse.id`、`wms_inventory.sku_id → wms_sku.id`，但不加 cascade，只做 restrict。
2. **逐步添加**：每次加一个 FK 前先审计历史数据是否满足约束，避免迁移失败。
3. **不加 FK 的关系**：库存流水与库存行、分配与出库单等由 Service 层事务保证的关系，不需要额外 FK。

### 风险

- 应用层遗漏引用检查时，可能产生孤儿行（如已删除的 SKU 仍被库存行引用）。
- 当前已有测试覆盖主要删除路径，但不能保证所有代码路径都正确检查。
- 不建议由 AI 自动给所有表批量加 FK，尤其不要加 cascade，容易改坏删除语义。
