# Go 代码约定与阅读路线

本项目使用 Go 1.26，保留按业务模块组织的单体应用。目标是让业务规则、错误和资源生命周期容易追踪。以下是本项目的约定，不是所有 Go 项目都必须遵守的唯一结构。

## 目录和依赖

- `cmd/wms` 负责启动、信号处理和资源关闭；`internal/app` 负责组装依赖及路由。
- `handler` 负责 HTTP 参数、身份信息和响应；`service` 负责业务规则及需要跨操作保持一致的事务；`repository` 负责持久化操作。
- 事务内的 Repository 方法接受同一个 `*gorm.DB`；事务外的查询使用请求的 `context.Context`。不要在同一业务事务中混入新的数据库连接。
- 保留现有跨模块接口。新增接口应来自实际调用方需求，不要求每个 Service 或 Repository 都实现一个接口。
- 不引入通用 CRUD 基类、泛型 Repository 或微服务拆分。先用具体类型和普通函数表达业务。

## 命名和格式

- 使用 `gofmt`；修改 import 时按标准库、第三方库、本项目分组，可运行 `goimports -local gowms`。
- 用 `ID`、`URL`、`HTTP` 等常见缩写；变量名应体现含义，例如任务集合叫 `tasks`，不叫 `now`。
- 不为排版统一而修改已有 JSON 字段或数据库列名，它们是兼容性边界。
- 注释优先说明业务约束和选择原因。不要写“未来拆微服务”“完全安全”等实现尚不能保证的承诺。
- 只有确实可能失败的构造过程才返回 error；构造函数不要隐式启动无法停止的后台循环。


## DTO 和转换逻辑

- 同名字段相似不代表同一契约。入库单和出库单都有 `CreateOrderReq`、`OrderDetailItem`、`OrderQuery`，但来源、幂等键和响应语义不同，保留在各自 `dto` 包，不建立全局订单 DTO。
- DTO 负责 HTTP 边界，model 负责持久化；转换逻辑放在拥有该业务流程的 service 中，避免让 model 依赖请求结构。
- 分页、ID、整数参数等真正的 HTTP 共性放在 `pkg/httpx`；只出现一次或业务含义不同的转换不要为了“复用”抽成通用函数。
- 批量操作 DTO 可以结构相似，但各模块的错误明细和事务策略独立，合并前必须确认 API 契约完全一致。
## 可选字段和共享状态

- 部分更新的 DTO 中，`Nickname *string` 表示是否提交该字段：nil 保留原值，指向空字符串则清空。`Status *int` 同样能区分未提交与明确设置为 0。不要让 Go 零值意外覆盖数据库值；普通非可选字段仍使用值类型。
- 多个字段共同维护一个不变量时，用一个互斥锁保护整组状态。雪花生成器的时间、序列、节点号必须一起看待，分别加 atomic 不能自动保证组合操作正确。
- 先校验关联对象，再修改关联；检查和写入之间有并发风险时放进同一事务并采用共同的锁协议。用户角色分配与删除角色是实际例子。
- 生成任务号不需要为了复用单号生成器而访问 Redis：直接复用已有任务 ID，使事务依赖更少、代码更容易解释。
- 限流的“检查次数 + 预占次数”应在同一临界区完成，慢查询和密码校验放在锁外。给 map 加 mutex 只能防止数据竞争，还要明确容量和过期清理；本项目采用请求触发清理，没有另起 goroutine。
- `*redis.Client` 作为 interface 传递时要注意 typed nil：一个值为 nil 的具体指针放进 interface 后，interface 本身不为 nil，调用方法仍可能 panic。构造函数接收可选客户端时，在进入 interface 前显式判断；本项目的 App 组装对 nil Redis 做了单独处理。

## 错误和事务

- 用 `errors.Is` 判断哨兵错误，用 `errors.As` 获取驱动错误。不要通过错误文本包含 `duplicate` 或 `deadlock` 判断类型。
- 仅将 `gorm.ErrRecordNotFound` 转为“记录不存在”。数据库故障、请求取消和死锁应保留原错误，供上层响应、日志或重试处理。
- 使用 `%w` 添加有价值的操作上下文。无需在每一层重复包装或打印相同错误。
- 客户端返回业务错误的 `Code`、`Msg`；未知错误返回通用消息。完整内部错误留在服务端日志，批量接口同样遵守。
- 事务重试按“整笔事务重新执行”理解，回调需要重新读取状态。不要把非幂等的外部副作用放进重试回调。
- 几行明确的错误处理可以重复；不必为了消除每个 `if err != nil` 创建额外抽象。

## Context 和后台任务

- 请求操作传递请求 context；启动独立后台任务时明确谁负责取消、等待和关闭依赖。
- 长期循环由应用入口启动，提供阻塞的 `RunX(ctx)`，用 `WaitGroup` 等待退出。
- HTTP 关停之后再停止日志消费者，最后关闭 MySQL、Redis。关停超时需要处理仍活跃的连接。
- 缓冲 channel 是有容量限制的内存队列。操作日志仍采用尽力记录策略，队列满、数据库故障、进程崩溃都可能丢日志；它不能替代事务内库存流水。
- 不要盲目删除所有 `context.Background()`：例如请求已取消后释放 Redis 锁，应使用独立但有超时的 context。

## 多租户和缓存

- MySQL 查询范围和 Redis key 都需要体现租户。条码只在租户内唯一，缓存 key 采用 `gowms:tenant:<tenant_id>:barcode:<barcode>`。
- 缓存命中时校验租户；平台旁路查询不使用条码缓存。更新 SKU 的名称等字段也需要失效缓存。
- 当前缓存采用 TTL 和更新后删除，属于最终一致性，尚不保证并发读写时的强一致性。
- GORM 回调有适用范围：原生 SQL、裸表查询、关联查询及平台旁路要单独检查，不能宣称自动覆盖全部访问路径。
- 请求有正租户 ID 时，Create 中显式指定其他租户会报错。后台跨租户工作领取任务后，应把任务租户写入执行 context。

## 验证和学习顺序

1. 从 `cmd/wms/main.go` 阅读启动和 defer 顺序，再看 `server.go` 的退出路径。
2. 从 `basic/service/sku.go` 阅读错误分类、租户缓存和相关测试。
3. 阅读 `system/service/audit.go`，理解 goroutine、channel、context 和关闭数据库的顺序。
4. 阅读 `pkg/tx/tx.go`，区分业务冲突、MySQL 死锁与普通故障。
5. 再沿入库、上架、分配、拣货、盘点链路学习事务和库存不变量。
6. 阅读 `inbound/service/import_worker.go` 与 `import_parse.go`，区分任务执行权、每行业务幂等、取消与重启恢复。

基本检查：`go test ./...`、`go vet ./...`、`golangci-lint run ./...`。MySQL 集成测试通过 `internal/testutil` 创建临时数据库；需要强制执行时设置 `WMS_TEST_REQUIRED=1` 和仅用于本地或测试环境的 `WMS_TEST_DSN`。

测试连接池最多使用 8 个业务连接，允许真实事务竞争，同时避免多个包同时运行耗尽 MySQL 连接。200 个并发调用不等于必须建立 200 个数据库连接；防超卖测试还应确认失败原因为库存不足，不能把连接错误也算作正确拒绝。

`go test -race ./...` 需要 CGO 和兼容的 C 编译器。它检查 Go 内存访问竞争，不能替代真实 MySQL 上的库存并发测试。CI 已包含入口包及内部模块的 race 测试。
