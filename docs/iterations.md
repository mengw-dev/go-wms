# 迭代记录与路线图

本文档记录项目在持续审查中的修复进展与后续计划，分两部分：已经完成的修复，以及待完成的迭代事项。当前能力与边界以 [需求与已知边界](requirements.md)、[API 文档](api.md) 与实际代码为准。

## 一、已完成的修复

### 1. 一致性、并发与库存

| 修复项 | 说明 |
| --- | --- |
| 收货数量语义 | 前端 `qty` 统一为含不良品的收货总量，残品只在上架量计算时扣除，修复了误判收齐与拒收。 |
| 盘点审核差异 | 差异与流水取同一份锁读结果，避免调整前后使用两个账面值；审核要求全部明细录入实盘数。 |
| FIFO 分配与租户 | FIFO 查询与数量更新显式过滤租户与软删，数量更新改为模型条件更新，不再绕过租户回调。 |
| 分配锁范围收敛 | 先非锁定取候选，只锁本次数量所需的前缀行，库位编码改由普通读补齐；补跨批次 FIFO 与「未使用的行不被锁」回归测试。 |

| 聚合关系校验 | 拣货锁内比较任务与分配行的 `order_id` / `sku_id` / `allocated_qty` / `detail_id`，不一致返回 40016；配套迁移回填历史任务的 `detail_id`。 |
| 库存约束 | 库存表非负与数量平衡 CHECK 约束由迁移建立，启动时校验；分配、上架按固定顺序加锁，死锁由整事务重试兜底。 |

### 2.2 业务正确性

#### 2.2.1 请求级幂等补全

拣货与任务领取已落地 `Idempotency-Key` + `wms_idempotency`；收货、上架、盘点审核待接入同一套实现。完整方案分三层，缺任何一层都会留下重复累加的口子：

| 层 | 位置 | 状态 | 覆盖范围 |
| --- | --- | --- | --- |
| 1. key 生命周期 | 前端 | 待实现 | 同一操作复用同一个 key、换参数必换 key、结果不确定时保留原 key 与原参数 |
| 2. key 级去重 | 服务端 `wms_idempotency` | 已落地 | 只覆盖同 key 重试，不覆盖跨 key |
| 3. 短窗口内容去重 | 服务端 Redis | 待实现 | 兜住「不同 key + 相同内容」，跨设备、跨缓存均有效 |

**第 1 层（前端 key 生命周期）**。把现在的「当前 key」改成按参数指纹索引的**待确认操作表**，持久化在 `localStorage`，命名空间为 `租户 + 用户`，条目键为 `scope + 对象 + 参数指纹`（稳定序列化，不含时间戳与随机数）。规则：

- 提交前先按条目键查：命中则复用该条目的 key，未命中则生成新 key，并**先落盘再发请求**；
- 只有「明确成功」与「明确业务拒绝」删除条目；超时、断网、5xx、关闭页面一律保留原 key 与原参数；
- 应用启动或进入任务时，若该对象存在未确认条目，提示「上一次提交结果未确认」，可用原 key 与原参数重发。

这样「同参 → 同 key、异参 → 异 key」由条目键自动成立，不需要额外判断。当前实现把 key 放在内存且一个对话框只用一个 key，`reset()` 还会无条件清空——既不支持跨刷新恢复，也会让第二次不同数量的拣货复用旧 key 而被 409 拒绝。

**第 2 层（服务端 key 级去重）**。`wms_idempotency` 唯一键 `(tenant_id, scope, idempotency_key)`，另存 `request_hash` 作内容比对。判定如下：

| key | 指纹 | 代表什么 | 处理 |
| --- | --- | --- | --- |
| 无记录 | — | 首次操作 | 执行业务，成功后在同一事务写记录 |
| 同 key | 同指纹 | 同一次操作的重复提交（重试、网络重发、双点击） | 回放首次结果，不执行业务、不累加 |
| 同 key | 不同指纹 | key 被复用到了不同内容 | 409 拒绝，不执行业务，前端应重置该 key |
| 不同 key | 同指纹 | 或为真重复（前端重新生成 key 后重发），或为真合法（分批拣货、分次收货） | 服务端无法从报文区分，按新操作执行，由第 1、3 层与业务数量上限兜底 |
| 不同 key | 不同指纹 | 两次不同的新操作 | 直接执行 |

几个边界：

- **并发同 key**：两个事务都查不到 → 都执行 → 后者唯一键冲突（1062）→ 映射为可重试冲突 → 整事务重试后查到记录并回放。因此幂等记录的插入必须与业务写入同一事务。
- **业务失败**：记录随事务一起回滚，key 可安全复用。
- **记录损坏或为空**：返回内部错误，不用「当前进度」兜底，否则会把损坏伪装成成功回放。
- **超过 7 天保留期被清理**：等同「不同 key + 同指纹」，会再次执行，所以幂等保证只覆盖保留窗口内。

**指纹的职责边界**：指纹只用于判断「复用同一个 key 的这次请求内容是否与首次一致」，**不用于跨 key 去重**。合法重复操作（同一任务先拣 5 件再拣 5 件）的指纹相同是预期行为，不是缺陷；不应往指纹里增加 operator、时间戳或序号，那会让合法重试被判成「内容不一致」而误拒。

**第 3 层（服务端短窗口内容去重）**。第 1 层堵不住「换设备、清缓存、换账号后以新 key 重发」，这一层用 `(租户 + scope + 操作人 + 指纹)` 在 Redis 上 `SET NX EX`，TTL 取数秒到几十秒。必须**按 scope 逐项开启**——它同时会挡住合法的连续同参操作：拣货这类客户端已强制携带 key、合法连续同参操作频繁的入口不应开启；收货、以及 key 可选或缺失的后台入口才适合开启，那里的重复几乎必然是重试。

**收货的部分进度风险**：收货的业务上限只拦「超过应收量」（`req.Qty > remaining`），拦不住「应收 100、实收 30、重复提交两次记成 60」。所以在接入第 1、3 层前，收货仍有虚增风险。

## 三、工程约定与能力边界

### 3.1 文件职责与依赖约定

长期有效，新增代码按此放置。

| 目录 | 放什么 |
| --- | --- |
| `modules/*/model` | 数据库模型、状态枚举、持久化字段 |
| `modules/*/dto` | HTTP 请求与响应结构，不放业务逻辑 |
| `modules/*/api` | 跨模块的稳定合约，不放数据库实现 |
| `modules/*/repository` | 查询、写入、锁读、持久化 |
| `modules/*/service` | 用例编排、校验、事务边界 |
| `modules/*/handler` | HTTP 绑定、鉴权、调用 service、返回响应 |
| `internal/pkg` | 有多个真实使用方的技术基础能力 |
| `modules/demo` | 明确标记的外挂编排层 |
| `cmd`、`internal/bootstrap` | 启动与依赖注入，不放业务逻辑 |

补充约定：

- 接口只在有真实消费者时才定义。只有一个调用方就在调用方那边写个小接口；跨模块稳定复用才放 `api` 包。不给每个 service 都机械地配一个接口。
- 一个导出的核心类型一个文件；强相关的私有结构体和方法可以放一起。按用例拆 `receiving.go`、`putaway.go`、`query.go` 是合理的，文件到三四百行或同时管几件事再拆。
- 抽公共包要同时满足四个条件：有两三个真实调用方、概念稳定、错误与事务语义一致、抽完不增加模块耦合。不新增 `common`、`utils`、`helper`、`base`、`shared` 这类没有明确职责的包。

### 3.2 尚未支持的能力边界

以下都是**当前的能力边界，不是缺陷**，对外描述中不应写成「已支持」。

- **请求级幂等**：key 级去重的天花板是「服务端无法从报文区分重试与真实新操作」。前端 key 生命周期与跨 key 的内容去重尚未实现，因此收货、上架在**部分进度**下的重复提交（如应收 100、实收 30、重复提交两次记成 60）仍有重复累加风险；已落地的拣货与领取只保证同 key 重试不重复执行。
- **单实例 / 多实例**：本地导入文件目录按单实例设计；导入 Worker 依赖共享存储；权限缓存与登录限流为进程内实现，多实例不共享额度、也没有统一的失效广播。
- **Snowflake**：仅在「单实例 + 唯一节点号」下可用，**不能写成「跨重启绝对唯一」**。
- **其它登记项**：软配额、best effort 操作日志、API Key 轮换、JWT 存 localStorage、密码强度、AI 库存数据外发、Redis 故障时的限流放行、脚本治理。
- **运维侧缺口**（数据库备份与 PITR、恢复演练、自动回滚与滚动发布、统一配置中心、证书自动续期等）已在 [生产就绪评估](production-readiness.md) 集中登记，此处不重复。
