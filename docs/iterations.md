## 一、已完成的修复

### 1. 一致性、并发与库存

| 修复项 | 说明 |
| --- | --- |
| 收货数量语义 | 前端 `qty` 统一为含不良品的收货总量，残品只在上架量计算时扣除，修复了误判收齐与拒收。 |
| 盘点审核差异 | 差异与流水取同一份锁读结果，避免调整前后使用两个账面值；审核要求全部明细录入实盘数。 |
| FIFO 分配与租户 | FIFO 查询与数量更新显式过滤租户与软删，数量更新改为模型条件更新，不再绕过租户回调。 |
| 分配锁范围收敛 | 先非锁定取候选，只锁本次数量所需的前缀行，库位编码改由普通读补齐；补跨批次 FIFO 与「未使用的行不被锁」回归测试。 |
| 拣货锁粒度 | 由锁整张出库单改为锁任务行，主单状态由条件原子更新收口，同单多任务可并行；2026-10-05 本地 k6 同参数对比曾记录吞吐 +66%、单次拣货平均耗时 -45%，属于历史结果，本轮未复测。 |
| 数量上限兜底 | 分配行、明细、主单三处数量累加统一补 `picked_qty + delta <= allocated_qty` 与 `delta > 0`；`RowsAffected` 为 0 时按业务码停止并整体回滚。 |
| 聚合关系校验 | 拣货锁内比较任务与分配行的 `order_id` / `sku_id` / `allocated_qty` / `detail_id`，不一致返回 40016；配套迁移回填历史任务的 `detail_id`。 |
| 库存约束 | 库存表非负与数量平衡 CHECK 由 SQL 迁移建立，迁移测试检查；release 启动不自动校验 CHECK。业务路径按约定顺序加锁，跨流程仍可能死锁，由整事务重试兜底。 |
| 任务进度 | 拒绝无效任务类型、空任务与非正数量，进度改为剩余量比较，消除整数溢出。 |

### 2. 幂等与防重

| 修复项 | 说明 |
| --- | --- |
| 拣货请求级幂等 | `wms_idempotency` 表 + `Idempotency-Key`，唯一键 `(tenant_id, scope, idempotency_key)`；同 key 同指纹回放首次结果快照，同 key 不同指纹 409；凭证与结果缓存随业务事务一起提交。 |
| 任务领取幂等 | 领取接口按 `outbound.claim` 操作域接入同一套幂等，重试回放首次凭证与租约，不轮换 token。 |
| 同 key 并发回放加固 | 后到者因快照读不到先到者记录而先被状态/数量校验拒绝时，业务回滚后用新读核对已提交记录：命中回放首次成功、指纹不同 409、读取失败保留原错误；回放快照按字段形状校验（缺字段/类型错误/`null` 均按损坏处理），租约过期不影响回放。 |
| 收货请求级幂等 | `inbound.receive` 接入同一套 `wms_idempotency`：指纹含单据/明细/数量/残品量/批次（批次按业务原有精确比较）；同 key 同内容回放空成功（`data:null` 契约不变，空成功用固定 `{}` 标记与损坏区分），收齐后重放不重复生成上架任务；同 key 改数量/明细/批次 409；`Idempotency-Key` 可选，无 key 调用方保持旧契约但无请求级去重。前端 `useReceive` + `ReceiveDialog` 按明细复用待确认操作记录（先落盘再发送、未知结果禁改参数、恢复/放弃、7 天窗口核对）。 |
| 上架请求级幂等 | `inbound.putaway` 接入同一套 `wms_idempotency`：指纹含任务/库位/数量；同 key 同内容回放空成功，不重复增加库存、流水或任务进度，完成后重放不重复写单据状态；同 key 改数量/库位 409；幂等记录与库存生效、库位占用、任务推进、单据状态同事务提交，中途失败整体回滚（含注入错误的回滚测试）。前端 `usePutaway` + `PutawayDialog` 按任务复用待确认操作记录。 |
| 幂等记录清理 | 后台 Worker 按 7 天保留期清理，24 小时一轮，启动先跑一次。 |
| PDA 前端操作生命周期 | `usePdaPick` 按「一次真实操作一个 key」管理领取/拣货：提交前把 key + 业务参数落盘（`pendingOperations`，按 user_id + 演示会话隔离），持久化失败不发送；确认成功后删除记录、下次同参操作生成新 key；超时/断网/5xx/401/403 与状态数量类拒绝保留原 key 原参数，只有服务端语义可确认未执行的静态校验类错误才结束操作；刷新/关闭重开按任务恢复待确认操作，超 7 天保留期只允许核对放弃不允许自动重发；凭证、租约、快照、请求序号按任务隔离，晚返回不污染新任务；租约过期/凭证不符被拒绝后清空凭证回到重新领取。存储读写非原子，不提供跨标签页互斥，多标签页并发由服务端 key 级去重兜底。 |
| 业务键幂等 | 出库单创建按 `biz_order_no` 租户内唯一键去重并在冲突后回查；Excel 导入按 `import_task_id + import_row` 唯一键保证补偿重跑不重复建单。 |
| 外部接入租户 | 外部 API Key 入口由服务端配置固定租户，`tenant_id=0` 也走精确隔离上下文。 |

以上只覆盖「同 key 重试」。跨 key 的重复提交仍是缺口，处理方案见 2.2。

### 2.2 业务正确性

#### 2.2.1 请求级幂等补全

拣货、任务领取、收货与上架已落地 `Idempotency-Key` + `wms_idempotency`；盘点审核待接入同一套实现。端到端方案包含客户端操作生命周期与服务端事务去重；短窗口内容拦截不是必需的第三层，也不能证明两次操作相同。

| 层 | 位置 | 状态 | 覆盖范围 |
| --- | --- | --- | --- |
| 1. key 生命周期 | 前端 | 已落地（PDA 领取/拣货、收货、上架） | 同一次真实操作原 key 原参数重试；成功后下一次真实操作新建 key；结果不确定时不开始替代操作 |
| 2. key 级去重 | 服务端 `wms_idempotency` | 已落地 | 只覆盖同 key 重试，不覆盖跨 key |
| 可选业务防误触 | 按具体业务定义 | 待需求确认，不默认实施 | 同参可能是合法分次作业，时间窗口不能充当操作身份 |

**第 1 层（前端 key 生命周期）**。按“一次真实操作”保存待确认记录，字段包括 `tenant_id + user_id + scope + task_id + operation_key + 原始请求参数 + 创建时间 + 状态`，采用账号/租户隔离的持久化存储。参数指纹用于检查内容一致，不能永久充当操作身份：同一任务先拣 5 件再拣 5 件是两次操作。规则：

- 提交前先恢复该对象的待确认操作；存在未知结果时只能原 key、原参数重试，不能通过改变数量另发新请求。创建新操作时先持久化，再发请求；持久化失败必须有明确处置。
- 明确成功后结束本次操作；下一次真实操作即使参数相同也生成新 key。超时、断网、5xx、关闭页面保留记录。明确未提交的业务拒绝可结束操作，但 409 内容冲突不能简单丢 key 后重发，应先核对原操作。
- 应用启动或进入任务时提示并恢复待确认操作；超过服务端 7 天保证窗口时不能自动重发，应先核对业务结果。
- 任务切换时绑定对应凭证、key 和快照；隔离旧请求的晚返回。领取响应重放不会续期，已完成领取后的新一次续领需要新 key。退出/换账号不显示或重放其他身份的记录。

已落地：`utils/pendingOperations.ts` 提供按身份（user_id + 演示会话 sessionNamespace）隔离的持久化记录（schemaVersion、scope、objectId、operationKey、业务参数、创建时间、状态），带运行时校验，损坏/版本不支持/写入失败都会阻止新操作并提示；`usePdaPick.ts` 按任务隔离凭证、租约、快照与请求序号，领取/拣货均「先落盘再发送」，错误按服务端语义分类（可确认未执行的静态拒绝才结束操作，其余保留原 key 原参数），成功/放弃才删记录；`PickDialog.vue` 提供待确认横幅与「恢复重试 / 已核对放弃」。边界：存储读写非原子，不提供跨标签页互斥；跨 key 同内容服务端仍视为新操作；记录只保证 7 天保留窗口。

**第 2 层（服务端 key 级去重）**。`wms_idempotency` 唯一键 `(tenant_id, scope, idempotency_key)`，另存 `request_hash` 作内容比对。判定如下：

| key | 指纹 | 代表什么 | 处理 |
| --- | --- | --- | --- |
| 无记录 | — | 首次操作 | 执行业务，成功后在同一事务写记录 |
| 同 key | 同指纹 | 同一次操作的重复提交（重试、网络重发、双点击） | 回放首次结果，不执行业务、不累加 |
| 同 key | 不同指纹 | key 被复用到了不同内容 | 409 拒绝本次内容，前端核对原操作，不自动换 key 重发 |
| 不同 key | 同指纹 | 或为真重复（前端重新生成 key 后重发），或为真合法（分批拣货、分次收货） | 服务端无法仅凭报文区分，按新操作执行；客户端必须保留操作身份 |
| 不同 key | 不同指纹 | 两次不同的新操作 | 直接执行 |

几个边界：

- **并发同 key（已加固）**：唯一键冲突映射为可重试冲突，由 TxRetry 回滚后重新查记录回放；先到者已提交、后到者因事务快照看不到记录而先被状态/数量校验拒绝时，业务事务回滚后改用事务外新读核对已提交记录——命中且指纹一致回放首次成功，指纹不同返回 409，读取失败或记录不存在则保留原业务错误，不伪造成功也不诱导换 key。已补同 key 并发（部分拣货/拣满剩余/异内容/并发领取）、幂等插入失败整笔回滚、租约过期回放与租户/scope 隔离的真实 MySQL 并发测试。幂等记录必须与业务写入同事务提交。
- **业务失败**：记录随事务一起回滚，key 可安全复用。
- **记录损坏或为空（已加固）**：返回内部错误，不用「当前进度」兜底。校验按字段形状执行：空串、非法 JSON、`null`、缺必需字段、字段类型错误（含 `done_qty` 为字符串/`null`）均视为损坏；数量 0 是合法值，不用零值判断缺失；领取记录缺失凭证或租约信息不可解析同样拒绝。回放仍不受租约是否过期影响（回放返回首次租约）。
- **超过 7 天保留期被清理**：等同「不同 key + 同指纹」，会再次执行，所以幂等保证只覆盖保留窗口内。

**指纹的职责边界**：指纹只判断同 key 的内容是否一致，不用于跨 key 去重。字段按具体命令选择：当前拣货包含任务、数量、规范化扫描内容和入口类型；领取包含任务与操作人。不要加入每次重试都会变化的时间戳或随机数；也不能一概禁止 operator，需以当前命令契约为准。

**暂不实施通用 Redis 内容去重**。收货同样允许连续两次收 30 件，短 TTL 会误拦合法作业；Redis 预占与 MySQL 提交也没有共同事务，失败/崩溃时需要额外恢复协议。换设备或清缓存后的恢复需稳定操作 ID、业务凭证或服务端待确认流程，不能承诺仅凭内容自动识别真实重复。若未来要做防误触提示，应作为明确的业务规则另行设计。

**收货的部分进度风险（已解决）**：业务上限过去只拦「超过应收量」，拦不住重复提交把 30 记成 60。现已接入客户端操作生命周期（`useReceive` + `ReceiveDialog` 按明细复用待确认操作记录）与服务端同事务去重（`inbound.receive`）：同 key 重试回放空成功不重复累计，新 key 再收按新操作合法累计，收齐后重放不重复生成上架任务；验证记录见 [开发与验证](development.md)。

#### 2.2.2 其余待办

- **外部出库单同号不同内容**。`outbound/service/integration.go` 目前只看 `biz_order_no` 就返回原单，先推 SKU A 两件、再推 SKU B 一百件会被当成重复成功。改为按规范化后的 `tenant_id + biz_order_no + warehouse_id + details + remark` 计算指纹：指纹一致返回原单，不一致返回 409，不同租户允许同号；时间戳、随机数不进指纹。
- **Web 健康检查**。nginx `/healthz` 静态 200 可作为前端自身存活检查；`.github/workflows/deploy.yml` 默认也以此作为部署健康地址，不能证明后端可用。另加端到端就绪探针或部署时分别检查前后端；验收必须包括 nginx 正常、后端故障时发布检查失败。

- **任务超过 200 条的查询**。详情只取 `DetailTaskPageSize` 的第一页并丢弃 total，PDA 弹窗依赖此结果。新增任务分页或显式截断契约，验证第 201 个任务可被获取和作业。
- **补并发与回滚测试**。已有拣货竞态和盘点锁等待/回滚测试；后续补上架中途失败后的库存/流水/任务整体回滚、真实死锁重试与耗尽，再按具体场景扩展盘点交错覆盖。文件不同名不等于没有测试。

## 三、工程约定与能力边界

### 3.1 文件职责与依赖约定

以下是概览；长期规则、允许的例外和拆分判断统一以 [Go 约定](go-style.md) 为准，目录导航见 [代码索引](code-index.md)。

| 目录 | 放什么 |
| --- | --- |
| `modules/*/model` | 数据库模型、状态枚举、持久化字段 |
| `modules/*/dto` | HTTP 请求与响应结构，不放业务逻辑 |
| `modules/*/api` | 跨模块的稳定合约，不放数据库实现 |
| `modules/*/repository` | 查询、写入、锁读、持久化 |
| `modules/*/service` | 用例编排、校验、事务边界 |
| `modules/*/handler` | HTTP 绑定、鉴权、调用 service、返回响应 |
| `internal/pkg` | 有多个真实使用方的技术基础能力 |
| `modules/demo` | 明确标记的外挂编排层 |
| `cmd`、`internal/bootstrap`、`internal/app` | 进程生命周期、数据库初始化与依赖组装；bootstrap 保留已有种子/演示重置职责，不新增普通业务用例 |

补充约定：

- 接口只在有真实消费者时才定义。只有一个调用方就在调用方那边写个小接口；跨模块稳定复用才放 `api` 包。不给每个 service 都机械地配一个接口。
- 按用例和变化原因拆文件，强相关类型可放一起。三四百行仅作为人工复核信号；优先保持事务与不变量可追踪，不强制一个导出类型一个文件。
- 抽公共包要同时满足四个条件：有两三个真实调用方、概念稳定、错误与事务语义一致、抽完不增加模块耦合。不新增 `common`、`utils`、`helper`、`base`、`shared` 这类没有明确职责的包。

### 3.2 尚未支持的能力边界

以下区分已确认的缺陷与尚未提供的能力，对外描述中不能一并写成「已支持」。PDA 生命周期属于上文已确认缺陷；多实例设施等按业务需求决定是否扩展。

- **请求级幂等**：服务端无法仅凭相同内容区分重试和真实新操作。前端操作生命周期待完善，收货/上架的服务端请求去重尚未接入，部分进度仍有重复累加风险；拣货/领取的同 key 保证限于记录保留窗口。跨 key 内容拦截不是默认补救方案。
- **单实例 / 多实例**：本地导入文件目录按单实例设计；导入 Worker 依赖共享存储；权限缓存与登录限流为进程内实现，多实例不共享额度、也没有统一的失效广播。
- **Snowflake**：进程内并发安全，跨实例要求节点号唯一；逻辑时间未持久化，重启仍有时钟与状态丢失边界，不能写成「跨重启绝对唯一」。
- **其它登记项**：软配额、best effort 操作日志、API Key 轮换、JWT 存 localStorage、密码强度、AI 库存数据外发、Redis 故障时的限流放行、脚本治理。
- **运维侧缺口**（数据库备份与 PITR、恢复演练、自动回滚与滚动发布、统一配置中心、证书自动续期等）已在 [生产就绪评估](production-readiness.md) 集中登记，此处不重复。

### 3.3 新增功能的固定动作

读代码索引与相关测试 → 想清楚类型放哪、依赖往哪走 → 明确事务与租户边界 → 判断是否需要幂等 → 补业务测试 → 同步 API 与架构文档 → 跑 `gofmt`、`go vet`、`go test` 与 lint。
