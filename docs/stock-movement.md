# 仓内移库

入口：“库存查询”明细行的“移库”；历史在“库存管理 → 仓内移库”。同一仓库内把可用库存从一个启用库位移到另一个启用库位，确认即完成。页面沿用日夜主题、手机布局和可拖动高度的局部滚动表格。

## 业务规则

- 单次仅移动一条来源库存的部分或全部可用量，正整数，最多 2147483647，原因必填、最多255字符。计量单位沿用货品单位。
- 保留仓库、货品和批次。来源现存量与可用量等量减少，目标等量增加，双方已分配量均不改变；不得移动已分配数量。
- 目标同仓库、同货品、同批次的库存存在时合并，不存在时创建。来源库存行清空后保留供追溯。
- 新建或空目标行继承来源入库时间；有货目标行合并时取两者较早时间。沿用现有“库位+货品+批次”汇总结构，这是批次行级FIFO，合并后不区分每件货的原入库时间。
- 仓库、来源/目标库位、货品必须属于当前租户且未删除、未禁用。目标不能是来源库位，也不能跨仓库。
- 确认时重新锁定和检查库存、引用及数量；前端展示的可移动量只是加载时快照。
- 每次成功写一张不可编辑的移库记录，以及关联同一移库号的 `MOVE_OUT` / `MOVE_IN` 成对流水。库存、占用状态、流水、记录在一个事务内提交，任一步失败整体回滚。
- 来源库位仍有任意现存库存（包括已分配库存）即保持占用；完全清空则空闲；目标变为占用。保留既有仓库锁协议，没有顺带修改B16锁粒度。

本版本不含草稿、审批、移库任务、自动推荐库位、库位容量校验、跨仓调拨和自动撤销。需要移回时，核实目标当前可用量后另发一笔反向移库，保留两次记录。

## 权限与API

路径前缀 `/api/v1`；所有ID在JSON中为字符串。只读用户可查历史与流水，执行移库需同时具备 `wms:inventory` 和 `wms:inventory:move`。内置演示/个人体验角色补充移库权限，自定义角色由管理员授予。专用来源/库位接口不要求基础资料修改权限。

| 方法 | 路径 | 参数与权限 |
| --- | --- | --- |
| GET | `/inventory/moves` | 库存查看权限；keyword匹配移库号/货品编码/名称/批次，warehouse_id、operation_key精确核对，page、page_size（1–100） |
| GET | `/inventory/move-source/:id` | 库存查看+移库权限；返回来源业务说明、可用量和可操作状态 |
| GET | `/inventory/move-locations` | 库存查看+移库权限；source_inventory_id必填，keyword匹配库位编码，page、page_size（1–100）；仅当前租户同仓其他启用库位 |
| POST | `/inventory/moves` | 库存查看+移库权限；`Idempotency-Key`必填，1–64字节；请求示例见下 |

```json
{"source_inventory_id":"100","target_location_id":"200","quantity":3,"reason":"库位整理"}
```

响应为已完成记录，包含移库号、来源/目标库存和库位、货品/批次、数量、原入库时间、操作人、原因、完成时间；不公开内部请求指纹和操作键。非法JSON、尾随第二个JSON及未知字段拒绝。列表返回 `list/total`。租户0也精确隔离，不作为跨租户移库入口。

## 重试与结果核对

`wms_inventory_movement` 的 `(tenant_id,operation_key)` 唯一键与业务事务共同保证同键最多执行一次。指纹覆盖来源、目标、数量、规范化原因和操作者用户ID；同键换参数/换操作者拒绝。重放读取原成功快照，后续可用量减少、资料禁用或操作人改名不导致再次移动。移库记录不参与通用七天幂等清理，按业务历史长期保留。

前端在发送前持久化原参数和请求编号，普通账号使用本机存储、演示账号使用会话存储。网络或不确定错误保留记录；页面刷新后可按原请求重试，或通过 `operation_key` 核对已提交记录。存储不可用/损坏时阻止新建；超过七天仍可核对记录，但界面保守地禁止重新发送。身份变更/离页后的旧响应不能清除原账号的待确认记录。

清除本机记录需要明确确认已人工核对，它不会撤销库存。多标签页各自新建不同请求编号代表不同操作，不能仅凭数量和目标相同自动去重；服务端仍校验可用量。演示“一键重置”是例外：只删除该隔离租户的移库记录并重置对应业务数据，不影响其他租户；重置后应重新加载并核对旧待确认记录。

带来源库存参数刷新页面且存在待确认操作时，优先显示核对入口，不自动弹出新的移库窗口。相关真实服务栈回归见[基础版收尾](release-acceptance.md)。

## 数据库升级

新增迁移 `000014_inventory_movements`，开发建表、正式建表、数量范围审计、正数量CHECK验证、演示重置同步。新服务启动前必须完成迁移。历史记录保留库存ID及业务名称快照，基础资料后续修改不会改写历史。

空表允许down；表中已有移库记录时down拒绝删除历史，应备份并采用前向迁移。迁移工具拒绝down后可能标记dirty，不能未经核查直接force跳过。

本功能分支基于main已有000013及本地仪表盘/表格高度提交。未合并的波次分支也有000014；未来合并波次必须给未发布迁移重新编号，不能同时发布两个000014。原工作区未提交的外部单000013候选同样需要合并时重新编号，本功能不包含它们。
