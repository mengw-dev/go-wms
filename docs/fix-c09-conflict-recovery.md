# C09 / I44：请求内容冲突的持久恢复

2026-11-03，基线8674285。只修改前端恢复逻辑，不改库存、幂等指纹、后端执行或数据库。C09的I12/I24/I25仍继续处理，不能据此标记整组完成。

## 根因与改动

服务端40901表示同一请求编号对应的内容不一致，原实现只在当前composable的内存中阻止重试，持久记录仍为uncertain。关闭重开、存储事件恢复或刷新后，blocked被清空，同一冲突请求又能发出。

- 待确认记录增加明确的`conflict`状态，保留原key、原业务参数、归属和创建时间。旧prepared/sending/uncertain恢复语义保持。
- 收货、上架、PDA领取/拣货、盘点审核在恢复与提交入口都检查持久冲突状态，未先调用界面restore也不能绕过；同族波次、库存异常/冻结命令和移库一起补齐。
- 异步结果按原操作key标记，不能使用同业务对象的最新key。迟到网络错误不能降级已记录冲突，已删除的记录不能凭迟到回复重建。没有新增通用工作流框架。
- 冲突恢复按钮禁用并提示核对；盘点冲突保留人工核对后放弃入口，移库仍允许只读查询原凭证。明确成功/拒绝、未知结果原key恢复、过期窗口和账号隔离继续保留。

## 兼容与边界

持久化容器/字段仍为v1，新增状态。旧客户端不认识conflict会拒绝读取该记录容器，需刷新到新版本；不能通过清空业务记录解决版本不兼容。旧数据可继续读取，不重算业务指纹、不生成新key规避冲突。

写失败明确提示无法保存本次结果，不再错误宣称“本次操作未发送”。只有成功落盘的标记才能跨刷新恢复；存储损坏/禁止写入的完整产品处理仍在M01/I45。localStorage整体读改写仍不是跨标签页互斥，本次不宣称解决同对象多key并发创建；放弃确认的原目标保护由C09/I12继续处理。
